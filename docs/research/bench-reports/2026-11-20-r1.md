Positioning takeaways: (1) **no tier-3 peer ships an OS-level sandbox** — fusion-code's verified Seatbelt (C6) is a differentiator on the whole track; (2) Aider is stale (8 months, no MCP/subagents) — drop from the A-grade comparison, keep for local-model harness gain measurements as legacy baseline; (3) Goose is the strongest local-model competitor (in-process runtime, LF-governed) — primary rival for the home-field metric; (4) Crush is source-available, not OSI-open — exclude from "open-source ranking" claims.

### Baseline diff

Baseline §5 `verify` cells resolved: all four cloud products confirmed sandboxing (Amp: none built-in — weaker than the baseline guessed); **Codex CLI ships built-in Ollama/OSS support** (stronger than expected — Codex is now also a local-model competitor, not cloud-only; its local harness quality joins the home-field metric scope); checkpointing verified for Claude Code + Gemini CLI, unverified for Codex/Amp. No baseline value needs correction — snapshots append here per the baseline's no-in-place-edit rule.

Cross-tier conclusions:
1. **OS sandbox is nearly unique**: verified Seatbelt only in fusion-code + the closed/Apache cloud tier (Claude Code, Codex, Gemini CLI); zero in all four open-source peers. fusion-code + Apache-2.0 = only combination of open source + OS-level sandbox on the track.
2. **Local-model race is heating up**: Codex CLI (Ollama/OSS), Goose (in-process oi-kit), opencode/Aider (providers). fusion-code's moat is not "runs local" — it is **MLX/Apple-Silicon depth + small-model harness adaptation (tier spec) + training flywheel**. Must be measured (report #2 item 1) before claiming it.
3. **Checkpoint/rollback parity**: fusion-code executor rollback (Phase 3/3b, opt-in) vs Claude Code default-on /rewind + Gemini /restore — UX gap: ours is opt-in env-gated, competitors default-on. Candidate improvement item.

## 3. First two measured work items

**Item 1 — Local-model harness gain (home-field metric, highest priority).**
Fixed task suite (~20 coding tasks, mixed difficulty), same MLX checkpoint (e.g. Qwen3 8B 4bit via fusion-mlx), three harnesses: fusion-code vs opencode vs Aider. Metric: task resolved rate + tokens/task + tool calls/task. Deliverable: reproducible eval script + first numbers table in report #2. Success criteria: suite runs end-to-end unattended; every number has the exact model build + harness version recorded.

**Item 2 — Token/tool efficiency baseline from session jsonl.**
Reuse the trajectory collector (`fusion-code trajectory collect`) to derive per-task token and tool-call distributions from real sessions on v0.8.5. This is the before-numbers for any harness optimization (prompt slimming, tier dispatch). Success criteria: script + one committed baseline JSON in `benchmarks/` (branch only); numbers reproducible by rerunning the script.

Both are research artifacts — no mainline code change; eval scripts land on this branch and go up as a PR.
