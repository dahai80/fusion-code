# Bench Report — Qwen3-32B compact-tier run (2026-11-23)

## Result

| Tier | Model | Score | Notes |
|------|-------|-------|-------|
| 8B | Qwen3-8B (compact) | 9/20 | baseline |
| 27B | Qwen3.8-27B-4bit-mtp (compact) | 14/20 | 0 timeouts, MTP spec-decode |
| 32B | Qwen3-32B-4bit (compact) | **9/20** | 6/20 tasks hit the 600s task timeout |

The tier curve is non-monotonic. Qwen3-32B underperforms Qwen3.8-27B despite more parameters.

## Interpretation

1. **Latency-dominated loss.** 32B runs at ~15 tok/s (no speculative decoding); 6 of 20 tasks exhausted the 600s task timeout. Qwen3.8-27B with MTP had zero timeouts. Crucially, transcript inspection shows 4 of the 6 timeouts (T05/T11/T18/T19) actually **completed the work** — the verifier passed on the sandbox files (e.g. T05 shows 11 turns of requests, correct final files, `resolved=true wall=600`); only the driver process hit the wall-clock cap after the work was done. So 32B's latency-free capability is at least 13/20 (9 clean + 4 confirmed-at-timeout), with T13/T17 unresolvable either way. The 9/20 raw score is a floor set by speed, not capability — but it is the score a real user with a 600s cap would see, so it stands as the tier number.
2. **Generation gap.** Qwen3-32B is an older-generation base; Qwen3.8-27B is a newer model family at smaller size. Tool-calling discipline tracks training generation, not raw scale. This is an anti-scale data point: bigger is not better across generations.
3. **Compact prompt generalizes.** Even with the latency handicap, 32B-compact (9/20) matches 8B-compact (9/20) and does not collapse, consistent with the prompt-diet lever being safe across tiers.

## Methodology caveats (all of them)

- **Invalid first runs.** Two earlier runs scored 1/20 and 4/20 and are retracted: the first hit a model that was not in the engine registry (engine started before the download finished); the second was degraded by a driver→engine direct-path issue (below).
- **Direct-path degradation.** Driven directly at :11434, the model emitted tool calls as plain text (`Write\n{"file_path": ...}`). Probes proved model and engine correct (byte-exact request replay, per-header replay, direct curl all return proper `tool_calls`); the same driver run through a header-stripping reverse proxy works and is the path used for the 9/20. Full evidence chain in `handoff-fusion-mlx.md` §6. Caveat: the 27B 14/20 baseline was measured direct; the 32B 9/20 via proxy. The proxy is transparent at the HTTP level, but the path asymmetry is recorded for honesty.
- **Concurrent load.** A `fusion-cowork desk-rpc` process shared the engine during parts of the run (Kimi-48B requests, 9s cadence). Memory pressure likely contributed to early eviction/reload churn in the retracted direct run; impact on the proxy run was not directly observed but cannot be excluded.

## Default-flip decision impact

No new support for flipping the compact-prompt default at 32B: the comparison tier that matters (newest-generation model) is 27B, where compact already beats full 14/20 vs 10/20. The 32B result adds a scaling-bounds data point (older-generation 32B < newer 27B) and strengthens the case for measuring tiers by generation, not parameter count.
