# Bench Report — Qwen3.8-27B baseline + engine-degradation verification (2026-11-23)

## Baseline (pre-fix engine)

| Run | Engine | Score | Notes |
|-----|--------|-------|-------|
| 2026-11-23T04-01-09-245Z | 0.10.68 | **17/20** | transcripts captured (PR #315) |
| (prior measurement, summary lost) | 0.10.6x | 14/20 | harness fixes since: commandLoopGuard rewrite, compact prompt |

Failures at 17/20: T05, T13, T17 — all 600 s timeouts, three distinct modes:

1. **T05 — pure latency.** On track, killed mid-verify. No format problem.
2. **T13 — engine degradation.** Plain-text tool call emitted twice with identical id `call_7aa4a8fa` on 27B request `[6fce3ceeca24]`, 20 s after concurrent Kimi parse failures `[bfac74dee0d9]` + scheduler row realignment.
3. **T17 — engine degradation.** Plain-text `call_7e4d0c5a` on 27B request `[b9aa2ac4427a]`, same chain (Kimi `[6232c309ec57]` parse failure → realignment → slip).

Passing-run behavior (transcripts): 20–38 assistant events, 4–8 Bash, 1–4 Read, 1–2 Edit. Tight single-track loops; cross-tier failures (T07/T12/T15/T20) all resolve on 27B — capability gap lives in 8B/32B generations, not the harness.

## Engine degradation (fusion-mlx #1694)

Trigger chain (2/2 pre-fix captures, then reproduced deliberately on 0.10.69): concurrent Kimi-Linear-48B tool-call traffic → tool-call parse failure on the Kimi request → scheduler batch-row realignment → 10–90 s later a 27B request emits a well-formed stream (`finish=stop`, no parse warning on itself) whose tool call is plain text in `call_<id>{json}` format. The tool call never executes; the task typically times out.

Verification history:

| Build | Loaded rerun (T13+T17 + ~2 req/s Kimi) | Unloaded rerun |
|-------|----------------------------------------|----------------|
| 0.10.69 `3ea0f01b` (fail-visibly fix) | 1/2, T17 slip reproduced (`call_8a0b9a9f` on `[e3629d9e5f26]`) | 2/2 clean |
| 0.10.69+ `b6edee57` (epoch invalidation, PR #1700) | 2/2, 0 slips, 7 realignments survived | — |

`b6edee57` verified within the achievable envelope: 710 Kimi requests + 7 realignments, 0 degraded emissions. The exact pre-fix chain (Kimi parse failure → realignment → slip) did not re-fire — the synthetic load produced zero Kimi parse failures in that run. Status: verified-pending-observation. Discriminator if it recurs: does `call_<id>` appear in the raw generated tokens (sampling slip) or only in `delta.content` (emission-path leak)?

## 8B cross-tier comparison (2026-11-24, transcript-captured)

Full 20-task 8B (Qwen--Qwen3-8B) run on engine 0.10.70, fusion-code v0.8.20
(includes #321 recovery): **7/20** (35%) vs 3/20 (15%) on v0.8.11 pre-#315.
Runs: `fusion-code-2026-11-24T03-01-58-567Z` (T01-T18) +
`fusion-code-2026-11-24T03-49-52-663Z` (T19-T20 retry; first attempt died to
an external engine SIGTERM restart at 11:46:47 local, #1256 watchdog).

Key deltas vs the 27B runs:

- **Zero timeouts, zero text emissions.** All 13 failures are genuine verify
  failures at ~80-335 s walls. The 600 s deaths that dominated the first 8B
  measurement are gone (harness fixes + #321 recovery + engine 0.10.70).
- **All 13 failures = max-turn exhaustion mid-work.** Transcript evidence:
  every failing task's last event is a tool call with no verify pass. T17
  burned 6 Writes without ever running tests; T16 6 Reads + 5 Edits, no test
  run; T12 7 Glob thrash; T19 8 Edits; T20 deleted the yaml then hit the
  turn cap. The cross-tier set T07/T12/T15/T20 all FAIL here, PASS on 27B —
  the gap is generation quality (edit accuracy / fewer wasted turns), not
  format handling.
- T05 (27B's thermal-latency failure) is an easy-ish medium on 8B timing —
  walls 66-270 s mean ~130 s, so thermal decay does not bite at this tier.

Engine hazard note: the external SIGTERM restart (ppid=1 launchd context,
#1256 attribution) killed two tasks again — second occurrence in as many 8B
measurement sessions. Recommendation to the engine team: identify the
launchd-side sender; bench runners should also retry on connection-refused
at session start.

## 8B failure-mode correction + nudge experiments (2026-11-24, later runs)

Three more 8B runs (baseline 7/20, final-turn cap nudge 8/20, failed-test
verify nudge 7/20 — PR #328): within the ±1 noise band, no measurable gain.

Corrections to the previous section:

- "Max-turn exhaustion" was over-diagnosed. The failing tasks mostly end
  **before** the cap: either the model declares success right after a failing
  test run (saw `Exit code 2`, still reported done), or commandLoopGuard
  kills the session mid pytest-loop ("stuck in a command execution loop").
  Both routes bypass the completion-report path where the verify-before-report
  nudge lives.
- Meta (`isMeta`) messages do not persist to session transcripts, so nudge
  firing cannot be verified from transcript capture — transcript-based
  textEmission counting is unaffected (tool_use/slips are regular content).
- Two nudge mechanisms shipped behind the same gates as the existing
  verify-before-report (local-mlx, 1 attempt): final-turn cap nudge (never
  fired in bench; safety net) and failed-last-test detection (logically
  sound, unproven). 27B regression run pending before tier conclusions.
